# نظام إدارة طابور المشفى (Hospital Queue Management)

نظام لإدارة طابور المرضى في مشفى بعدة عيادات/خدمات، يضم أربع شاشات:

| الشاشة | المسار | من يستخدمها |
|---|---|---|
| الكشك (قطع التذاكر) | `/kiosk` | حساب بدور `Kiosk` |
| النداء | `/employee/call` | حساب بدور `Employee` |
| العرض العام (اللوحة) | `/display` | حساب بدور `Display` |
| لوحة تحكم المدير | `/admin` وما تحتها | حساب بدور `Admin` |

كل شاشة تتطلب تسجيل دخول بحسابها الخاص (اسم مستخدم/كلمة مرور)، ومدير النظام هو من ينشئ هذه الحسابات ويحدد أدوارها.

## البنية التقنية

- **ASP.NET Core 8 / Blazor Server** — كل الشاشات مبنية بمكوّنات Blazor تعمل من طرف الخادم؛ التحديث اللحظي (نداء المريض، تحديث لوحة العرض) يعتمد على اتصال Blazor Server الدائم بالمتصفح نفسه، بدل فتح Hub SignalR منفصل — أي أن الميزة اللحظية التي طلبتها موجودة فعلياً وتعمل عبر WebSocket، لكن عبر قناة Blazor نفسها بدل قناة إضافية مكررة. راجع `HospitalQueue.Web/Services/QueueEventBus.cs` للتفاصيل.
- **PostgreSQL** عبر EF Core (Npgsql).
- **ASP.NET Core Identity** لتسجيل الدخول (كوكيز)، مع أدوار ثابتة (Admin/Employee/Kiosk/Display) وصلاحيات دقيقة إضافية مخزّنة كـ Role Claims يديرها المدير من شاشة "الأدوار والصلاحيات".
- **HospitalQueue.PrintBridge**: خدمة صغيرة منفصلة تعمل محلياً على جهاز الكشك نفسه (Windows) وتستقبل طلب طباعة من متصفح شاشة الكشك عبر `http://localhost:9100/print`، وترسل التذكرة كصورة (Bitmap) إلى الطابعة الحرارية عبر ESC/POS raw printing — رسم التذكرة كصورة بدل نص عربي مباشر متعمّد: أغلب طابعات ESC/POS الرخيصة لا "تُشكّل" الحروف العربية (الأشكال المتصلة) ولا تعالج الاتجاه من اليمين لليسار بنفسها، بينما GDI+ على ويندوز يفعل ذلك بشكل صحيح، فنطبع نتيجته كصورة نقطية مباشرة بغض النظر عن دعم الطابعة للعربية.

### هيكل المشروع (Solution)

```
HospitalQueue.sln
src/
  HospitalQueue.Domain/          الكيانات (Entities) والثوابت (الأدوار/الصلاحيات)
  HospitalQueue.Infrastructure/  DbContext + Identity + Seed Data
  HospitalQueue.Application/     منطق الأعمال: QueueService, ReportService
  HospitalQueue.Web/             تطبيق Blazor Server (كل الشاشات)
  HospitalQueue.PrintBridge/     خدمة الطباعة المحلية لجهاز الكشك (Windows فقط)
```

## المتطلبات

- .NET 8 SDK
- PostgreSQL 14+ (أو `docker compose up -d` لتشغيل حاوية جاهزة، راجع `docker-compose.yml`)

> ملاحظة: هذا الكود تم كتابته في بيئة لا تملك اتصال إنترنت ولا .NET SDK مثبّت، لذلك **لم يتم تنفيذ `dotnet build` فعلياً على هذا الكود قبل تسليمه**. راجع الكود وشغّل `dotnet build` عندك أولاً قبل النشر، وأبلغني بأي خطأ تصحيح تحتاج مساعدة فيه.

## التشغيل محلياً

```bash
docker compose up -d                 # تشغيل PostgreSQL
cd src/HospitalQueue.Web
dotnet run
```

عند أول تشغيل، `SeedData` يقوم تلقائياً بـ:
- إنشاء مخطط قاعدة البيانات مباشرة من النموذج الحالي (`EnsureCreatedAsync`، وليس Migrations — راجع قسم "قبل الإنتاج" أدناه).
- إنشاء الأدوار الأربعة (Admin/Employee/Kiosk/Display) مع صلاحياتها الافتراضية.
- إنشاء حساب مدير افتراضي:
  - اسم المستخدم: `admin`
  - كلمة المرور: `ChangeMe!2026`
  - **غيّر كلمة المرور فوراً من شاشة "المستخدمون" بعد أول دخول.**
- إنشاء 3 عيادات تجريبية (الباطنية، الأطفال، المختبر) و3 شبابيك مرتبطة بها، لتكون الشاشات جاهزة للتجربة مباشرة.

يمكن تغيير بيانات الحساب الافتراضي عبر `appsettings.json` (`Seed:AdminUsername`, `Seed:AdminPassword`, `Seed:AdminEmail`) أو متغيرات البيئة المقابلة قبل أول تشغيل.

## قبل الإنتاج: التحويل إلى EF Core Migrations

حالياً قاعدة البيانات تُنشأ عبر `EnsureCreatedAsync()` لأن بيئة التطوير التي كتبت فيها الكود لا تملك `dotnet-ef`. هذا يعمل تماماً للتجربة والتطوير، لكن قبل الإنتاج يفضّل التحويل لـ Migrations الحقيقية حتى تقدر تُحدّث المخطط تدريجياً لاحقاً دون فقدان البيانات:

```bash
dotnet tool install --global dotnet-ef
cd src/HospitalQueue.Web
dotnet ef migrations add InitialCreate -p ../HospitalQueue.Infrastructure -s .
```

ثم افتح `HospitalQueue.Infrastructure/Data/SeedData.cs` وبدّل `EnsureCreatedAsync()` إلى `MigrateAsync()`.

## شرح الشاشات

### شاشة الكشك (`/kiosk`)
المريض يختار الخدمة/العيادة من أزرار كبيرة، فتصدر تذكرة برقم متسلسل يومي لكل خدمة (مثال: `A-014`)، وتتم محاولة طباعتها فوراً عبر خدمة الطباعة المحلية. إن تعذر الاتصال بالطابعة يظهر تنبيه للمريض بتدوين الرقم يدوياً، لكن التذكرة تبقى مسجّلة في النظام دون تأثر.

### شاشة النداء (`/employee/call`)
الموظف يبدأ جلسة عمل باختيار الشباك ثم الخدمة (كل شباك مرتبط مسبقاً بخدمة أو أكثر من شاشة "الشبابيك" بالإدارة). بعدها يستخدم:
- **استدعاء التالي**: يسحب أقدم تذكرة منتظرة لنفس الخدمة وينادي عليها (تظهر فوراً على شاشة العرض).
- **إعادة نداء**: لنفس التذكرة الحالية.
- **بدء الخدمة / إنهاء الخدمة**: مع إمكانية إضافة ملاحظات عند الإنهاء.
- **تخطي (لم يحضر)**: لتذكرة نودي عليها ولم يحضر صاحبها.
- **تحويل**: ينهي التذكرة الحالية ويصدر تذكرة جديدة لعيادة أخرى، وتدخل بآخر الطابور هناك.

### شاشة العرض (`/display`)
لوحة واحدة موحّدة تعرض كل الشبابيك معاً، كل شباك في بطاقة منفصلة تُظهر آخر رقم نودي عليه واسم الخدمة، مع وميض وصوت تنبيه (نغمة + نطق صوتي عربي عبر متصفح المستخدم) عند كل نداء جديد.

### لوحة تحكم المدير (`/admin` وما تحتها)
- **لوحة التحكم** (`/admin`): بطاقات إحصائية (عدد المنتظرين الآن، قيد الخدمة الآن) ومخططات أعمدة (بدون أي مكتبة JS خارجية، لتعمل حتى لو شبكة المشفى معزولة عن الإنترنت) لعدد التذاكر، متوسط زمن الانتظار، متوسط زمن الخدمة — لكل عيادة، ولكل موظف، ولكل شباك — ضمن مدى تاريخ قابل للاختيار.
- **المستخدمون** (`/admin/users`): إنشاء حسابات وتعطيلها وتصفير كلمات المرور وتحديد أدوارها (شاشة الموظف/الكشك/العرض/المدير — يمكن لحساب واحد أن يحمل أكثر من دور).
- **الأدوار والصلاحيات** (`/admin/roles`): تعديل الصلاحيات الدقيقة الممنوحة لكل دور (Role Claims)، وإضافة أدوار مخصصة جديدة.
- **الخدمات والعيادات** (`/admin/services`): إضافة/تعديل/تعطيل العيادات ورموزها المستخدمة في رقم التذكرة.
- **الشبابيك** (`/admin/counters`): إضافة/تعديل/تعطيل الشبابيك، وتحديد أي خدمة/عيادة يخدمها كل شباك.

## إعداد خدمة الطباعة (HospitalQueue.PrintBridge)

تُثبَّت وتُشغَّل على **جهاز الكشك نفسه** (وليس على خادم التطبيق)، لأنها تحتاج الوصول المباشر لطابعة USB المتصلة بذلك الجهاز تحديداً.

1. على جهاز Windows، ثبّت الطابعة الحرارية عادياً (تعريف الشركة المصنّعة، أو تعريف Windows العام "Generic / Text Only" يكفي).
2. افتح `src/HospitalQueue.PrintBridge/appsettings.json` وضع اسم الطابعة **كما يظهر تماماً** في "الطابعات والماسحات" بويندوز، في حقل `PrinterName`.
3. شغّلها:
   ```bash
   cd src/HospitalQueue.PrintBridge
   dotnet run
   ```
   أو انشرها كملف تنفيذي مستقل (`dotnet publish -c Release -r win-x64 --self-contained`) وأضفها لبدء التشغيل التلقائي لويندوز (Task Scheduler أو مجلد Startup) حتى تعمل تلقائياً عند تشغيل جهاز الكشك.
4. تأكد أن متصفح شاشة الكشك يعمل على **نفس الجهاز** (لأن الطلب يذهب إلى `http://localhost:9100`).

⚠️ **لم تُختبر الطباعة فعلياً على طابعة حقيقية** (لا تتوفر بيئة Windows ولا طابعة في بيئة التطوير هذه). راجع `EscPosBuilder.cs` و`RawPrinterHelper.cs` واختبرهما مع طابعتكم الفعلية؛ قد تحتاج تعديل عرض الورق (`PaperWidthDots`، القيمة الشائعة 384 نقطة لورق 58مم أو 576 لورق 80مم) أو أمر القطع (`GS V`) حسب موديل الطابعة تحديداً.

## نقاط معروفة تحتاج متابعة لاحقاً

- **الصلاحيات الدقيقة (Permissions)** مخزّنة وقابلة للتعديل من شاشة "الأدوار والصلاحيات"، لكن حماية الشاشات حالياً تعتمد على الدور نفسه (`[Authorize(Roles=...)]`) وليس على كل صلاحية فرعية بشكل مستقل. لو احتجت تحكماً أدق (مثلاً موظف يقدر يعرض التقارير لكن لا يستدعي مرضى)، تحتاج ربط هذه الـ Claims بسياسات تفويض (Authorization Policies) مخصصة — البنية التحتية لذلك جاهزة (الصلاحيات محفوظة كـ Role Claims) لكن الربط الكامل لكل شاشة لم يُنفَّذ بعد.
- لا توجد اختبارات آلية (unit/integration tests) بعد.
- طباعة ESC/POS غير مُختبرة على جهاز حقيقي (انظر أعلاه).
- لتحويل الواجهة لثنائية اللغة (عربي/إنكليزي) لاحقاً: النصوص مكتوبة مباشرة داخل الشاشات وليست عبر ملفات موارد (resources)، فتحتاج إعادة تنظيم إن رغبت بدعم لغة إضافية.

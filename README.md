# نظام إدارة طابور المشفى (Hospital Queue Management)

نظام لإدارة طابور المرضى في مشفى بعدة عيادات/خدمات، يضم أربع شاشات:

| الشاشة | المسار | من يستخدمها |
|---|---|---|
| الكشك (قطع التذاكر) | `/kiosk` | كلمة سر عامة (تُضبط من `/admin/settings`) |
| النداء | `/employee/call` | حساب بدور `Employee` |
| العرض العام (اللوحة) | `/display` | كلمة سر عامة (تُضبط من `/admin/settings`) |
| لوحة تحكم المدير | `/admin` وما تحتها | حساب بدور `Admin` |

شاشتا النداء ولوحة التحكم تتطلبان تسجيل دخول بحساب مستخدم (اسم مستخدم/كلمة مرور)، ومدير النظام هو من ينشئ هذه الحسابات ويحدد دورها — كل حساب يحمل دوراً واحداً فقط. أما الكشك والعرض فهما شاشتا جهاز مشترك بلا حساب مستخدم: تُفتحان بكلمة سر عامة واحدة لكل شاشة يضبطها المدير من `/admin/settings` (راجع `HospitalQueue.Web/Shared/ScreenPasswordGate.razor`).

## البنية التقنية

- **ASP.NET Core 8 / Blazor Server + MudBlazor** — كل الشاشات مبنية بمكوّنات Blazor تعمل من طرف الخادم، باستخدام مكتبة [MudBlazor](https://mudblazor.com) (أزرار، جداول، بطاقات، مخططات، Snackbar...) بدل CSS يدوي بالكامل، مع هوية بصرية خاصة بهذا التطبيق (كحلي داكن + برتقالي دافئ، خط Cairo) معرّفة في `HospitalQueue.Web/Shared/AppTheme.cs` و`wwwroot/css/site.css`. التحديث اللحظي (نداء المريض، تحديث لوحة العرض) يعتمد على اتصال Blazor Server الدائم بالمتصفح نفسه، بدل فتح Hub SignalR منفصل — الميزة اللحظية تعمل فعلياً عبر WebSocket، لكن عبر قناة Blazor نفسها بدل قناة إضافية مكررة. راجع `HospitalQueue.Web/Services/QueueEventBus.cs` للتفاصيل.
- **PostgreSQL** عبر EF Core (Npgsql).
- **ASP.NET Core Identity** لتسجيل دخول حسابات المستخدمين (كوكيز)، مع أدوار ثابتة (Admin/Employee/Kiosk/Display). كل حساب يحمل دوراً واحداً فقط. شاشتا الكشك والعرض لا تستخدمان حسابات مستخدمين أصلاً — تُفتحان بكلمة سر عامة مخزّنة (مُجزّأة عبر `PasswordHasher`) في `OrganizationSettings` بدل ذلك.
- **طباعة التذاكر عبر متصفح الكشك مباشرة** (`window.print()`) بدل خدمة Windows منفصلة: صفحة الكشك تحقن إيصال التذكرة في الصفحة الحالية مع تنسيق `@media print` يخفي كل شيء عداها ويضبط حجم الصفحة لرول حراري 80مم، راجع `wwwroot/js/print.js`. هذا يعمل مع أي طابعة معرَّفة كافتراضية في نظام التشغيل — لا حاجة لتعريف ESC/POS خاص. للطباعة الفورية بدون نافذة تأكيد، شغّل متصفح جهاز الكشك بوضع kiosk مع خيار الطباعة الصامتة (التفاصيل أدناه).
- **إعدادات عامة قابلة للتعديل** (`/admin/settings`): اسم الجهة الذي يظهر في التذاكر وشاشة العرض، وشريط إخباري اختياري أسفل شاشة العرض.
- **هوية بصرية قابلة للضبط**: شعار المنظمة وألوانها يُحفظان في `OrganizationSettings` ويُطبَّقان على كل الشاشات دون تعديل الكود — الألوان تعيد تعريف متغيّرات CSS (`--hq-primary` و`--hq-accent` ومشتقاتهما) وقت التشغيل فوق الألوان الافتراضية في `wwwroot/css/site.css`. راجع `HospitalQueue.Web/Services/BrandingService.cs` و`Shared/BrandLogo.razor` و`Shared/BrandStyles.razor`.

### هيكل المشروع (Solution)

```
HospitalQueue.sln
src/
  HospitalQueue.Domain/          الكيانات (Entities) والثوابت (الأدوار/الصلاحيات)
  HospitalQueue.Infrastructure/  DbContext + Identity + Seed Data
  HospitalQueue.Application/     منطق الأعمال: QueueService, ReportService
  HospitalQueue.Web/             تطبيق Blazor Server (كل الشاشات) + MudBlazor
```

## المتطلبات

- .NET 8 SDK
- PostgreSQL 14+ (أو `docker compose up -d` لتشغيل حاوية جاهزة، راجع `docker-compose.yml`)

> ملاحظة: هذا الكود تم كتابته في بيئة لا تملك اتصال إنترنت ولا .NET SDK مثبّت، لذلك **لم يتم تنفيذ `dotnet build` فعلياً على هذا الكود قبل تسليمه**. راجع الكود وشغّل `dotnet build` عندك أولاً قبل النشر، وأبلغني بأي خطأ تصحيح تحتاج مساعدة فيه.

## التشغيل محلياً

```bash
docker compose up -d                 # تشغيل PostgreSQL
cd src/HospitalQueue.Web
dotnet run
```

عند أول تشغيل، `SeedData` يقوم تلقائياً بـ:
- إنشاء مخطط قاعدة البيانات مباشرة من النموذج الحالي (`EnsureCreatedAsync`، وليس Migrations — راجع قسم "قبل الإنتاج" أدناه).
- إنشاء الأدوار الأربعة (Admin/Employee/Kiosk/Display) مع صلاحياتها الافتراضية.
- إنشاء حساب مدير افتراضي:
  - اسم المستخدم: `admin`
  - كلمة المرور: `ChangeMe!2026`
  - **غيّر كلمة المرور فوراً من شاشة "المستخدمون" بعد أول دخول.**
- إنشاء 3 عيادات تجريبية (الباطنية، الأطفال، المختبر) لتكون الشاشات جاهزة للتجربة مباشرة.

يمكن تغيير بيانات الحساب الافتراضي عبر `appsettings.json` (`Seed:AdminUsername`, `Seed:AdminPassword`, `Seed:AdminEmail`) أو متغيرات البيئة المقابلة قبل أول تشغيل.

## موصى به: التحويل إلى EF Core Migrations (مرة واحدة فقط)

بدون Migrations حقيقية، قاعدة البيانات تُنشأ عبر `EnsureCreatedAsync()` — وهذا **لا يحدّث** قاعدة بيانات موجودة أصلاً عند إضافة جدول جديد بتحديث لاحق (تحتاج تحذف القاعدة وتعيد إنشاءها من الصفر كل مرة، وتفقد بياناتك التجريبية). بما إن ميزات جديدة راح تستمر تضيف جداول، يُفضّل تسوي هالخطوة **الآن مرة وحدة**:

```bash
dotnet tool install --global dotnet-ef
cd src/HospitalQueue.Web
dotnet ef migrations add InitialCreate -p ../HospitalQueue.Infrastructure -s .
```

هذا ينشئ مجلد `Migrations/` بالمشروع. بعدها **احذف قاعدة البيانات الحالية مرة أخيرة** (نفس أمر `DROP DATABASE hospital_queue;`) وشغّل `dotnet run` — الكود يكتشف تلقائياً وجود Migrations ويستخدمها بدل `EnsureCreated`. من هذه اللحظة فصاعداً، أي جدول جديد أضيفه لاحقاً تكفي معه:

```bash
dotnet ef migrations add <اسم_وصفي> -p ../HospitalQueue.Infrastructure -s .
```

ثم `dotnet run` عادي — يطبّق التحديث تلقائياً **بدون** حذف بياناتك الحالية.

## تسجيل الدخول

- `/Account/Login`: تسجيل الدخول العادي (اسم مستخدم + كلمة مرور) — يُستخدم لحسابات المدير والموظف.
- `/kiosk` و`/display`: لا تسجيل دخول بحساب هنا — أول زيارة للصفحة تعرض شاشة قفل تطلب كلمة السر العامة لتلك الشاشة فقط (تُضبط من `/admin/settings`)، ثم تبقى الشاشة مفتوحة طوال الجلسة (حتى إغلاق التبويب أو تحديث الصفحة).
- **مفتاح الجهاز**: للأجهزة المخصّصة (شاشة جدارية أو جهاز كشك بلا لوحة مفاتيح) لكل شاشة مفتاح مستقل يُنسخ من `/admin/settings`؛ فتح الرابط `‎/display?key=...‎` يتخطّى شاشة القفل مباشرة. المفتاح منفصل عن كلمة السر ليمكن إبطاله وحده بتوليد مفتاح جديد.

## شرح الشاشات

### شاشة الكشك (`/kiosk`)
المريض يختار الخدمة/العيادة من أزرار كبيرة، فتصدر تذكرة برقم متسلسل يومي لكل خدمة (مثال: `A-014`)، وتتم طباعتها فوراً عبر طباعة المتصفح. زر "ملء الشاشة" في الزاوية يضع الصفحة بوضع Fullscreen لتشغيلها ككشك فعلي.

### شاشة النداء (`/employee/call`)
الموظف يختار العيادة التي يعمل عليها من أعلى الشاشة نفسها، فتبدأ جلسة العمل فوراً (لا توجد صفحة منفصلة لبدء الجلسة، ويمكنه تبديل العيادة في أي وقت ما دام لا توجد تذكرة قيد المعالجة). بعدها يستخدم:
- **استدعاء التالي**: يسحب أقدم تذكرة منتظرة لنفس الخدمة وينادي عليها (تظهر فوراً على شاشة العرض).
- **إعادة نداء**: لنفس التذكرة الحالية.
- **بدء الخدمة / إنهاء الخدمة**: مع إمكانية إضافة ملاحظات عند الإنهاء.
- **تخطي (لم يحضر)**: لتذكرة نودي عليها ولم يحضر صاحبها.
- **تحويل**: ينهي التذكرة الحالية ويصدر تذكرة جديدة لعيادة أخرى، وتدخل بآخر الطابور هناك.

### شاشة العرض (`/display`)
لوحة واحدة تعرض آخر رقم تم نداؤه بشكل كبير مع نبض وتوهج، بجانب قائمة بآخر النداءات (يتميّز فيها لون التذكرة إذا كانت "إعادة نداء")، وحالة كل تذكرة (تم النداء/قيد الخدمة/انتهت/لم يحضر/تم التحويل) تتحدّث لحظياً مع كل تغيير، مع وميض وصوت تنبيه (نغمة + نطق صوتي عربي عبر متصفح المستخدم) عند كل نداء جديد. أسفل الشاشة شريط إخباري اختياري يُفعَّل ويُحرَّر من `/admin/settings`.

### لوحة تحكم المدير (`/admin` وما تحتها)
- **لوحة التحكم** (`/admin`): بطاقات إحصائية (عدد المنتظرين الآن، قيد الخدمة الآن) ومخططات أعمدة (MudBlazor Charts) لعدد التذاكر، متوسط زمن الانتظار، متوسط زمن الخدمة — لكل عيادة ولكل موظف — ضمن مدى تاريخ قابل للاختيار، إضافة إلى سجل تذاكر مفصّل (رقم الدور، الخدمة، التاريخ ووقت بدء الخدمة، الحالة، من قام بخدمته، زمن الانتظار وزمن الخدمة بالدقائق) بنفس مدى التاريخ.
- **المستخدمون** (`/admin/users`): إنشاء الحسابات، وجدول يعرض بيانات كل حساب مع زر إعدادات صغير يفتح نافذة لتعديل: الاسم الكامل، الدور (موظف/كشك/عرض/مدير — دور واحد لكل حساب)، **العيادات المخصّصة**، كلمة مرور جديدة، وتفعيل/تعطيل الحساب. تخصيص العيادات مفعَّل لحسابات الموظف والمدير فقط (وهما وحدهما من يفتح شاشة النداء)، والموظف لا يرى فيها سوى العيادات المخصّصة له؛ وترك الاختيار فارغاً يعني السماح بكل العيادات.
- **الخدمات والعيادات** (`/admin/services`): إضافة/تعديل/تعطيل العيادات ورموزها المستخدمة في رقم التذكرة.
- **الإعدادات العامة** (`/admin/settings`): اسم الجهة والشريط الإخباري في شاشة العرض، وكلمتا سر شاشتي الكشك والعرض ومفاتيح الأجهزة المخصّصة (روابط جاهزة للنسخ إلى تطبيق الأندرويد)، و**الهوية البصرية**: رفع شعار المنظمة (يظهر في شاشة الدخول ولوحة التحكم والكشك وشاشة العرض) وتحديد اللون الأساسي ولون التمييز اللذين يُطبَّقان على واجهة النظام بالكامل.
- **مصمّم الوصل** (`/admin/receipt-designer`): تصميم شكل التذكرة المطبوعة من عناصر جاهزة (اسم الجهة، اسم الخدمة، رقم التذكرة، التاريخ والوقت، نص ثابت، خط فاصل، مسافة، وشعار/لوغو يُرفع كصورة) مع تحكم بالترتيب والمحاذاة وحجم الخط والتعريض (وعرض الشعار بالمليمتر)، ومعاينة حيّة ببيانات تجريبية. يمكن إنشاء أكثر من قالب وتفعيل واحد منها فقط — الكشك يطبع دائماً بالقالب المفعّل.

## تفعيل الطباعة الصامتة على جهاز الكشك (اختياري)

بشكل افتراضي `window.print()` يفتح نافذة تأكيد الطباعة القياسية. لتفادي ذلك على جهاز كشك مخصص:

1. اضبط الطابعة الحرارية كطابعة **افتراضية** في Windows، وفي إعدادات التعريف اختر مقاس الورق كـ"رول/مستمر" (Continuous) وليس مقاساً ثابت الطول (وإلا كل تذكرة تُطبع بطول ورقة كامل فارغ).
2. شغّل متصفح جهاز الكشك (Edge أو Chrome) بوضع kiosk مع خيار الطباعة الصامتة، مثلاً:
   ```
   msedge.exe --kiosk-printing --kiosk "https://<عنوان-الخادم>/kiosk"
   ```
   بهذا الشكل تُطبع التذكرة مباشرة دون أي نافذة تأكيد.
3. بدون هذا الخيار، تظهر نافذة طباعة عادية عند كل تذكرة — يعمل النظام تماماً لكن يحتاج ضغطة إضافية من المريض/الموظف المشرف على الكشك.

## نقاط معروفة تحتاج متابعة لاحقاً

- **الصلاحيات الدقيقة (Permissions)** ما زالت تُزرَع كـ Role Claims في قاعدة البيانات (`SeedData.cs`)، لكن لا توجد شاشة لإدارتها وحماية الشاشات تعتمد على الدور نفسه (`[Authorize(Roles=...)]`). لو احتجت تحكماً أدق لاحقاً، البنية التحتية جاهزة لكن تحتاج ربط هذه الـ Claims بسياسات تفويض (Authorization Policies) مخصصة.
- لا توجد اختبارات آلية (unit/integration tests) بعد.
- خط Cairo وأيقونات Google Fonts تُحمَّل من الإنترنت (CDN) عند فتح الصفحة؛ إن كانت شبكة المشفى معزولة تماماً، حمّل خط Cairo محلياً وعدّل `Pages/_Layout.cshtml` و`Pages/_AccountLayout.cshtml` ليشيرا لملف محلي بدل رابط fonts.googleapis.com.
- لتحويل الواجهة لثنائية اللغة (عربي/إنكليزي) لاحقاً: النصوص مكتوبة مباشرة داخل الشاشات وليست عبر ملفات موارد (resources)، فتحتاج إعادة تنظيم إن رغبت بدعم لغة إضافية.
